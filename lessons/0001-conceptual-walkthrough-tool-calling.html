Lesson 01

Mental Model of Tool Calling & The Eval Loop

How LLMs orchestrate tools, why v0 fails, and how the evaluation harness grades your agent.

Duration: 10 mins Topic: Tool-Calling Architecture Reference: Architecture Reference

1. The Fundamental Mental Model

A common beginner misconception is that an LLM "executes code" or "calls APIs directly". It does not. An LLM is purely a text-in, text-out neural network. Tool calling is a protocol:

Phase 1

Schema Declaration

We declare tools in tools.yaml. The provider translates these definitions into JSON Schema so the model knows what functions exist.

Phase 2

Structured Intent

The model outputs a structured JSON object: {"name": "inspect_device", "args": {"asset_id": "LP-1042"}}.

Phase 3

Local Execution

Our Python code in agent.py inspects the JSON, calls the corresponding Python function in tools/, and intercepts any errors.

2. Why the Starter (v0) Fails Out of the Box

In starter_v0, the agent is intentionally crippled with two incomplete artifacts:

  • Vague tool descriptions in tools.yaml: For example, clarify is described merely as "Gửi một câu hỏi cho người dùng" without stating when it should be used (e.g., when asset ID is missing, or before executing destructive actions).
  • Incomplete system prompt in system_prompt.md: The baseline prompt lacks instructions for multi-turn conversations, doesn't mandate asking for user confirmation before creating tickets, and has no safety perimeter preventing internal policy leakages.
Key Takeaway: You do NOT need to rewrite agent.py or run_eval.py. The entire point of the lab is to diagnose failures produced by v0, formulate targeted hypotheses, and refine system_prompt.md and tools.yaml through versions v1 → v2 → v3.

3. The Eval Harness & Failure Modes

When you run run_eval.py, it loads test cases from data/eval_base.json and evaluates the agent's output against ground truth. Here are the core failure categories you will encounter:

  • wrong_tool: The user asked to check network status, but the model called search_kb instead of check_service_status.
  • wrong_arg_value: The model called the right tool, but passed invalid arguments (e.g., passing "outlook" instead of "email").
  • missing_info: The user stated "My computer cannot boot", but didn't provide an asset ID. Rather than calling clarify to request the asset ID, the model either hallucinated an ID or failed to act.
  • wrong_boundary: The user asked to create a ticket, but the agent created it immediately without asking for confirmation first.

4. Quick Concept Check

Scenario Practice

A user types: "My laptop screen is flickering, please inspect it." (Notice: no Asset ID is provided in the prompt). According to production IT helpdesk safety guidelines, what should the agent do?
